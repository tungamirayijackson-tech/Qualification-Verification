§ 01  /  What was built

A register of signed assertions, not a database of truths

The system does not decide whether a qualification is real. It proves that a named institution signed a statement, that the statement has not been revoked, and that no one has edited the history since — each answer attributable to a key, an actor and a moment in time. That was the design premise, and the delivered system holds to it exactly.

Everything in the manuscript's trust model is now enforced in code, not merely described. Four parties hold four different powers, and each boundary is carried by an authorisation rule, a database constraint or both.

PartyMay assertMay neverEnforced by, as built
InstitutionThat it conferred a qualification, on a date, at an NQF levelAlter or delete a credential once issuedIts Ed25519 key; every issuance signed and ledgered
RegistrarRecords, revokes and shares — for its own institution onlyTouch another institution’s records at allToken scope + a not-found response on anything out of scope
VerifierNothing. Only presents a certificate idBrowse or enumerate the registerNo anonymous listing exists; rate-limited public door
AuditorThat the ledger is intact, or is notWrite anything, anywhereRead-only role; recomputes the chain; every write path is 403
 One clarification the build made explicit: recording a qualification is the registrar’s act, not the administrator’s. An administrator admits an institution and issues its keys; what that institution awards is the institution’s own business to declare.

As-built premise

Every answer the system gives is attributable to a key and a timestamp, and any later edit to the record is made evident by the chain. That is a smaller claim than “verification” usually implies — and it is one the running system demonstrates on demand.

§ 03  /  Architecture, as built

One service, five modules, boundaries a test enforces

A single deployable Spring Boot service, internally partitioned into five modules whose dependency rules are checked by ArchUnit on every build — so the structure below cannot silently rot into a ball of mud. The domain layer imports no framework at all, which is what keeps the interesting logic unit-testable with no container load.

# backend/src/main/java/zw/ac/qvs/   — hexagonal per module
credential/
  domain/        Credential, Serial, NqfLevel, NationalId  (pure Java records)
  application/   RegisterCredential, RevokeCredential, SearchCredentials
  adapter/in/    CredentialController, QualificationController, ImportController
  adapter/out/   JPA repositories, field encryption
verification/
  domain/        CredentialUnderVerification, ShareToken, VerificationReport
  application/   VerifyCredential, IssueShareToken, RenderReport
  adapter/in/    PublicVerificationController  (the only unauthenticated entry)
ledger/          AppendEntry (Propagation.MANDATORY), VerifyChain, ExportTrail
identity/        AuthenticateUser, CreateUser, ManageAccount, BootstrapAdmin
shared/          Ed25519 signer, AES-GCM, Hashing, RFC-6238 TOTP, config

Decision — modular monolith, and it held

One image, five enforced modules. The maintainability story is defensible because the boundaries are mechanical: the build fails when a module reaches into another’s adapters, and fails again if the module graph grows a cycle. Microservices would have spent a third of the project on orchestration that nothing here needs.

§ 04  /  Verification mechanism

What “valid” actually resolves to

The verdict is the conjunction of four independent checks, and the response names which one failed rather than returning a bare boolean. This is the difference between verification and a database lookup that trusts its own table.

CheckWhat it provesHow it fails
signatureThe canonical JSON verifies against the institution’s published keyOne changed character of name or NQF level breaks it
issuerStandingThe signing key was valid, and the institution accredited, on the award dateA key that had not yet been issued, or lapsed accreditation
revocationThe credential has not been withdrawnA later revocation — a separate fact from signature validity
ledgerPresenceThe issuance entry is present and the chain recomputesAny tamper with the register’s history
 Observed live on 3.6.199.254: a freshly issued credential returned VALID with all four PASS; after revocation the identical certificate id returned REVOKED while its signature still verified — because the institution did award it, and later withdrew it. 
// canonical signed form: sorted keys, ISO-8601 dates, no insignificant whitespace
{
  "ser": "ZW-PR0142-2026-000001",       // serial: country, provider no, year, count
  "iss": "urn:qvs:inst:0142",
  "sub": "sha256:9f2c...a1",             // salted hash of the national ID, never the ID
  "nqf": 7, "crd": 360,
  "awd": "2026-04-11",
  "kid": "inst-0142-2026-a"              // key id, so rotation stays verifiable
}
detached_jws = ed25519( canonical_bytes, private_key[kid] )   // JDK-native, Nimbus JOSE envelope

Decision — key rotation designed in, and a same-day guard added

Every signature carries its kid, and keys hold validity intervals, so a credential signed today still verifies after two rotations. The build added one refusal the manuscript did not foresee: rotating a key twice in one day would give the new key a valid_until before its valid_from. That is now refused in words, naming the earliest valid date, rather than surfacing as a database constraint violation.

§ 05  /  The audit ledger

A history that can prove it was not edited

Each entry stores the hash of its predecessor, so altering entry n invalidates every hash from n onward. A tamperer must rewrite the whole tail; the auditor detects it by recomputing one chain, and the endpoint reports the first sequence number that stops being trustworthy. On the live server, verify-chain reported the chain intact across all entries after the full functional run.

-- V7__audit_ledger.sql  (Flyway) — the immutability trigger
CREATE FUNCTION deny_mutation() RETURNS TRIGGER AS $$
BEGIN RAISE EXCEPTION 'audit_entry is append-only (seq %)', OLD.seq; END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER audit_entry_immutable
  BEFORE UPDATE OR DELETE ON audit_entry
  FOR EACH ROW EXECUTE FUNCTION deny_mutation();

Appends happen inside the same transaction as the state change they describe — AppendEntry is declared Propagation.MANDATORY, so forgetting the surrounding transaction fails loudly rather than recording nothing. The cost is a serialisation point on seq; at this scale it is irrelevant, and the report says so plainly rather than pretending the design scales unboundedly.

§ 06  /  Localised for Zimbabwe

The same system, speaking the local vernacular

The manuscript was written against a South African setting. The delivered system is Zimbabwean throughout — and localisation here is not a string swap but a set of small correctness decisions, each with its own test.

DimensionAs builtNote

6.1The national ID is one value type, not two regexes

The identity number is never stored — only a salted hash of it. A hash is useful only if the same person hashes identically every time, and the two paths that hashed one already disagreed: search trimmed its input and registration did not. With thirteen bare digits that difference was invisible; with a format carrying optional hyphens, spaces and a check letter of either case it becomes a graduate who is plainly in the register and a search that reports nobody. Both paths now hash one canonical form.

NationalId.parse("63-1234567 K 42").canonical()  // "631234567K42"
NationalId.parse("631234567k42").canonical()     // "631234567K42"  — same person
NationalId.parse("8001015009087")                // refused: the old 13-digit form is not one

Honest limit — the check letter is not recomputed

Zimbabwe’s check letter is derived from the digits, so in principle a wrong one could be refused. It is not: the published descriptions of that derivation disagree, and a validator built on the wrong one would refuse genuine identity numbers held by real graduates — a worse failure than accepting a mistyped one. The shape is checked; the arithmetic is not claimed. That decision is recorded, not hidden.

§ 07  /  Security, as enforced

Four roles, an institution wall, and a public door built to be attacked

ControlImplementation, as builtWhat it stops
AuthenticationSpring Security resource server; 15-min access JWT, 7-day rotating refresh tokenLong-lived stolen tokens
AuthorisationRole matrix in one file, plus an institution-scope check in the use caseA registrar reaching another institution’s records
Institution wallRead, revoke and share all take the caller’s institution from the token; out-of-scope is not-foundEnumeration via guessable serials
MFAHand-rolled RFC-6238 TOTP, mandatory for REGISTRAR and ADMIN, enrolled on first sign-inCredential forgery via one leaked password
Account lifecycleSuspend, restore, reset password, reset second factor — each ledgered, sessions revokedA departed registrar who keeps signing; a lost phone that locks out
Rate limitingRedis token bucket, 60 req/min on the public path, 10/min on report generationBulk checking; report-CPU abuse
Data at restNational ID as a salted hash; display name AES-256-GCM encrypted; bcrypt cost 12Bulk personal-data harvesting
SecretsNone in the repository, ever; generated on the server at deploy; .env git-ignored and verified absent from the remoteThe commonest way a student project leaks credentials

Decision — out-of-scope is indistinguishable from not-found

A serial names the institution and counts from one, so it is guessable by construction. When a registrar asks for another institution’s credential — to read it, revoke it or publish it — the answer is the same 404, in the same words, as an unknown serial. A “forbidden” would confirm the serial exists, which is the one thing a guessable identifier must never do. This was a real gap in an earlier build, closed and covered by tests (see §11).

§ 09  /  Testing & traceability

Fast tests carry the logic; slow tests carry the wiring

The suite is tiered by what each tier is good at, and the ratio is the point: unit tests own the domain logic and run in seconds; integration tests run against a real PostgreSQL 16 in a Testcontainer, so they exercise the actual schema, the append-only trigger and the real SQL rather than an in-memory substitute that behaves differently.

 Coverage is measured on **/domain/** and **/application/** and excludes DTOs and config, so the number reflects tested logic. The traceability task fails the build if any requirement loses its test.

9.1The tests that matter most

  • Tamper tests. Mutate a stored claim; assert the signature check fails. Mutate a ledger row; assert VerifyChain reports that exact seq. These prove the security claims rather than restating them.
  • The institution boundary. Two universities, a registrar each: one cannot read, revoke or share the other’s credential, and the refusal is asserted identical to an unknown serial.
  • The role matrix. A parameterised test over role × endpoint; adding an endpoint without a matrix row fails the build.
  • National-ID canonicalisation. Three punctuations of one number must hash the same; the old thirteen-digit form must be refused.

9.2Traceability, generated not typed

Tests carry a @Requirement("FR-06") annotation; a Gradle task cross-references them against the requirement register and fails the build if any FR has zero covering tests. The delivered report reads 23 of 26 requirements covered, 0 planned, 0 uncovered — the three not marked “covered” are non-functional targets verified by measurement (the k6 latency stage, the cohort-import timing) rather than by an annotated unit test, and are noted as such rather than counted as green.

§ 11  /  Defects found & fixed

The bugs the build found, and what each one cost

These were found by driving the system as a real operator and against a running container, not only by unit tests. Naming them is the honest half of a technical report — and two of them were genuine security gaps.

DefectCauseFixClass
Cross-institution reachSerial-addressed endpoints checked the caller’s role but not their institution; serials are guessableScope check in the use case; out-of-scope answers not-found, identical to unknownsecurity
Every refusal was a 500Two exception advices tied at lowest precedence; the catch-all wonOrdered the module handler first; a controller-local handler that cannot be lostcorrectness
Auditor’s screen brokeA screen branched on “is admin” when it meant “is bound to one institution”Branch on the capability, not the role; the auditor is cross-institutioncorrectness
Console shipped unstyledAngular’s critical-CSS inliner emits an inline onload the strict CSP blocksinlineCritical: false; guarded by a test — found by screenshotting the containercorrectness
National-ID mismatchSearch trimmed its input, registration did not — a latent split once the format allowed separatorsOne NationalId value type; both paths hash the canonical formcorrectness
Rename collateralA blanket find-and-replace corrupted the RFC-6238 test vector and 64-char hash fixturesReverted; lesson recorded — a numeric literal is never a safe replace anchorprocess

The one worth stating plainly

The cross-institution gap is the classic shape of the flaw: authorisation asked what role is this and never whose record is this. Role checks are cheap and visible in one file, which is exactly why they get mistaken for the whole answer. The fix lives in the use case, not the controller, so a second adapter cannot forget it.

The sentence to end on

This system does not decide whether a qualification is real. It makes every assertion about one attributable to a key, a person and a moment in time — and makes any later edit to that record evident. That is a smaller claim than “verification” usually implies, and it is one the running system demonstrated, end to end, on demand.
